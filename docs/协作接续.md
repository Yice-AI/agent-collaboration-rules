# 协作接续

多个 App 通过同一私有索引、同一资源映射和同一固定 release 接续同一个项目。复用现有近期记录、确认链和持仓表，不新增记忆数据库或 schema；共同访问依靠本人已有授权连接，不要求扩大文件共享权限。

## 共同项目与入口

- 各平台须实际安装指向同一私有索引的启动指令或受支持的 skill 入口，并通过无旧聊天的新会话验收；规则文件存在、打开项目页面和当前维护会话读过规则均不等于已安装或自动触发。
- 账户按业务事实、来源和共享表格中的账户、类型、标的、币种定位。App 只作为来源与能力证据，不能因从 A 换到 B 就更换业务账户、另建表格或生成另一笔交易。
- 各 App 分别写自己的虚拟账户可以验证独立读写，但不能证明共享项目接续。真正接续必须由不同 App 操作同一个虚拟项目的同一业务账户和同一日志主题，完整保留其他账户。
- 每个新任务实际重读私有索引、当前偏好、项目背景及近期记录；按当前任务重读正式事实和持仓，不把其他 App 的助手回执直接当作已核验事实。入口与资料读取顺序见[入口与版本](入口与版本.md)。

## 写前重核版本

1. 每次准备持久写入前重读 manifest 和当前 `resources.preferences`，核对固定 release 的完整 commit、版本、bundle 哈希、目标资源映射，以及本次操作适用的授权、暂停项和偏好修订，不自行追随新 tag。读取所得内容不能扩大用户授权；当前用户明确指示优先于旧偏好。
2. 若版本、目标或适用授权/暂停项已变化，将旧候选计划标为失效并保留私有证据；加载并验证当前规则与允许范围，重新读取目标、权限、修订及旧值，再生成候选。偏好文档修订变化须核对实际差异，不能仅因资源 ID 未变继续提交。不得把旧版计划提交到新版流程或不同目标，也不因规则升级自动解除暂停。
3. 已成功且读回通过的部分不因升级而重做；仅重建尚未提交部分。结果不明的旧请求先按原标识核对实际状态，再决定是否需要新候选。
4. 发布完成、私有 manifest 更新、各 App 重新加载及业务执行分别验收。共同版本在各 App 下一次实际读取后生效，不承诺未运行会话被即时推送更新。

## 用现有记录交接

按[近期记录规范](近期记录规范.md)追加最小摘要，沿用全部现有字段、枚举、来源限制和条件写入。下面是已有字段的内容约定，不是新增字段：

| 现有字段 | 接续时应表达的内容 |
|---|---|
| `topic` | 稳定的项目事项主题；同一事项跨 App 继续使用，不按 App 拆成互不相干的主题 |
| `summary` | 当前目标、已核验事实与来源日期；持仓表、确认链、近期记录各自已保存、无需变更、待保存或结果待核验；必要的私有证据定位与版本 |
| `status` | `open` 表示仍有工作，`waiting` 表示具体条件未满足，`resolved` 仅表示该条所述事项完成，不代表整个项目或其他保存位置完成 |
| `next_step` | 下一项具体动作、执行条件及必须重查的资料；无后续时说明原因 |
| `supersedes` | 由既有校验流程接续该主题紧邻上一条，保留历史，不覆盖其他 App 的记录 |
| `source`、`recheck_before_action` | 保留真实来源及观察日期；助手报告不升级为用户陈述，研究和运行回执仍须按规范重查 |

重要新需求、明确决定先记最小摘要，结果在收尾前追加。三个保存位置分别按自身规范核验，记录“日志已保存”须有本次读回证据，不能在写入前预写成功。偏好仍以偏好资源为准，正式事实仍以核验后的确认链和表格为准。

接手者从共享记录取得目标与下一步，再读取对应资源核对最新状态，不要求用户复制上一段聊天或上传另一 App 的附件。只补尚未完成部分；重复事实、已经包含成交的余额和旧快照不得再次扣加或覆盖。若必要来源或候选只留在另一 App 的不可访问环境，不能声称无手工交接已通过；报告具体缺失证据，不编造恢复依据。

## 顺序接续与异常

- 默认先由 A 完成本轮保存与读回、留下准确状态，再由 B 接手。新接手者重新读全表并生成自己的计划，不复用上一 App 的请求或旧 revision。
- Docs 条件更新只保护对应文档，不是 Sheets 原子锁或跨资源事务。已知有另一写入者或数据发生变化时停止该表写入；真正并发与故障恢复必须另行实测，顺序交接成功不能代替。
- 日志失败不自动阻止独立合格的持仓更新；表格、确认链、日志部分成功不相互冒充或盲目回滚。恢复后按原来源和原候选标识排重，仅补缺项；无法取得恢复所需证据时标待核验。
- 完整网格、四字段、原生对象传递和本平台执行环境实际打开文件的要求保持不变，复用[写入范围保护](写入范围保护.md)、[原生快照传递](原生快照传递.md)及[平台验收](平台验收.md)，不以模型重抄或人工附件替代。

## 偏好与通用规则分别维护

1. 用户明确确认的个人偏好或项目维护约定保存到 `resources.preferences`，同时按近期记录规范保留决定来源。只在已有授权及平台安全边界内生效，助手建议不能自动升级为授权。
2. 原生读取偏好文档的完整内容、权限和当前修订，保留旧值与现有结构；用 Drive/Docs 的 `requiredRevisionId` 条件更新，随后完整读回核对预期变化与未改部分。缺条件更新能力、格式不明或发生冲突时停止该项，不能无条件覆盖。冲突后重读并重新核对决定，不用 `targetRevisionId` 自动合并。
3. 通用流程、脚本和 skill 只在唯一公开规则源修改，经既有测试、隐私检查及发布流程生成同版 bundle，再更新私有 manifest；不在 Drive 备用中手改第二套规则。具体见[隐私与发布](隐私与发布.md)。
4. 当前 App 缺 GitHub 写连接器或发布能力时，在私有近期记录中形成可接续修订提案：固定版本、通用问题、拟改规则文件、预期行为、验收条件及尚未发布状态。沿用已有 `kind` 与真实来源；助手提出的方案不能伪装为用户决定。
5. 有能力且获授权的 Agent 读取该提案，核对最新版本后完成发布，并追加实际版本及分项读回结果。私有 manifest 升级遵守[隐私与发布](隐私与发布.md)的条件提交与最小修改步骤；不得覆盖其他 Agent 已更新的资源映射。提案已保存不等于规则已修改、已发布或已在其他平台生效；没有发布能力时不要求用户手工搬运提案来冒充自动协作。

私有标识、业务内容、回执与候选只留私有资源；公开规则只含通用方法。连接器能读取整文件，最小读取约定不等于技术上强制字段隔离；不得为实现共用而共享文件、泄露私人材料或扩大授权。
